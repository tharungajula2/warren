Use `EXPLAIN` (or equivalent) to view the execution plan of a query. This shows which indexes (if any) are used and the estimated cost. The plan also shows join methods (nested loop, hash join, etc.) and whether tables are scanned. A query running slowly often indicates missing indexes, inefficient joins, or large scans on big tables.

### Permanent rule

Put indexes on columns used frequently in `WHERE`, `JOIN`, or `ORDER BY` clauses (primary keys are automatically indexed).

### Permanent trap

Assuming an index will always be used: if statistics are outdated or the query doesn’t use the indexed column properly (e.g. function on column), the optimizer might do a full scan.

### Never confuse

**Index Scan** — uses an index to retrieve specific rows.

---

**Sequential (Table) Scan** — reads every row of the table.

### Jurisdiction variants

**No delta.** Index usage and execution plan analysis are general across RDBMS; the concept of cost-based optimization is universal.
