### Core mechanism

Assume `customer_risk` contains `customer_id`, `valid_from`, `valid_to`, and `risk_grade`. If periods are non-overlapping, match the snapshot date inside the validity interval:

```sql
SELECT
    s.account_id,
    s.reporting_date,
    r.risk_grade
FROM loan_snapshots s
JOIN loan_accounts a
  ON a.account_id = s.account_id
JOIN facilities f
  ON f.facility_id = a.facility_id
LEFT JOIN customer_risk r
  ON r.customer_id = f.customer_id
 AND r.valid_from &lt;= s.reporting_date
 AND (r.valid_to &gt; s.reporting_date OR r.valid_to IS NULL)
WHERE s.reporting_date = '2026-08-31';
```

The half-open interval `valid_from &lt;= date &lt; valid_to` avoids double matching when one record ends on the same boundary at which the next begins.

Some sources store only change dates, not `valid_to`. Then select the latest record on or before the observation date:

```sql
WITH candidates AS (
    SELECT
        s.account_id,
        s.reporting_date,
        r.risk_grade,
        ROW_NUMBER() OVER (
            PARTITION BY s.account_id, s.reporting_date
            ORDER BY r.valid_from DESC
        ) AS rn
    FROM loan_snapshots s
    JOIN loan_accounts a ON a.account_id = s.account_id
    JOIN facilities f ON f.facility_id = a.facility_id
    LEFT JOIN customer_risk r
      ON r.customer_id = f.customer_id
     AND r.valid_from &lt;= s.reporting_date
)
SELECT account_id, reporting_date, risk_grade
FROM candidates
WHERE rn = 1;
```

This assumes at most one effective record for a customer at a given start time. Duplicate or overlapping effective periods must be treated as a data problem, not resolved by arbitrary ranking.

### Permanent rule

A historical observation may use only information effective on or before its observation date unless the analysis explicitly requires hindsight.

### Never confuse [As-of join] and [Current-state join]

**As-of join** - attaches the version valid at the historical observation date.

---

**Current-state join** - attaches whichever version is current now, regardless of when the loan observation occurred.

### Permanent trap

Joining history to a dimension table that contains only the latest customer record. The query runs cleanly but rewrites the past with present information.

### Jurisdiction variants

No delta. Effective-dated join mechanics do not vary by regulator.

<Recall
  q="What problem does an as-of join solve?"
  a="It prevents future or current information from being attached to a historical loan observation when that information was not yet effective."
/>

<Recall
  q="Why use a half-open validity interval?"
  a="`valid_from <= date < valid_to` gives one clean boundary and avoids matching both an ending record and its successor on the same date."
