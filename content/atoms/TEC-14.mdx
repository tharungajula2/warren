### Core mechanism

A month-end portfolio with September scheduled cash flow can be written as staged logic:

```sql
WITH month_end AS (
    SELECT
        account_id,
        reporting_date,
        outstanding_balance,
        days_past_due
    FROM loan_snapshots
    WHERE reporting_date = '2026-08-31'
),
september_due AS (
    SELECT
        account_id,
        SUM(scheduled_amount) AS scheduled_amount_sep
    FROM repayment_schedule
    WHERE due_date &gt;= '2026-09-01'
      AND due_date &lt; '2026-10-01'
    GROUP BY account_id
),
portfolio AS (
    SELECT
        m.account_id,
        m.outstanding_balance,
        m.days_past_due,
        d.scheduled_amount_sep
    FROM month_end m
    LEFT JOIN september_due d
      ON d.account_id = m.account_id
)
SELECT *
FROM portfolio;
```

Each CTE has a declared shape: `month_end` is one row per account for the selected date; `september_due` is one row per account; therefore the final join should preserve account grain.

CTEs do not automatically materialize data or make a query faster. Many optimizers inline them, and repeated references may still be expensive. Use them first for correctness and readability, then inspect the execution plan if performance matters.

Avoid creating dozens of one-line CTEs that merely rename columns. A useful stage should correspond to a real population, grain change, aggregation, ranking, or business transformation that deserves inspection.

### Never confuse [CTE] and [Temporary table]

**CTE** - a named result scoped to the statement and often optimized as part of that statement.

---

**Temporary table** - a separately created stored intermediate object with its own lifecycle and physical behaviour.

### Permanent rule

Name CTEs for the business stage they represent, and know the grain of each stage before joining it onward.

### Permanent trap

Assuming a CTE fixes performance by itself. It improves structure, but execution cost still depends on the optimizer, data volume, filters, joins, and repeated work.
