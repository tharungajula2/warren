### Core mechanism

```text
Governed upstream output
    ↓
Reporting transformations and aggregation
    ↓
Final extract or payload
    ↓
Validate population, fields, totals and format
    ↓
Reconcile to upstream control points
    ↓
Release only with explained differences
```

| Validation | What it catches |
| :--- | :--- |
| Record count / population | Dropped or duplicated rows |
| Key-field comparison | Incorrect identifiers or classifications |
| Aggregate reconciliation | Sign, unit or aggregation errors |
| Reference-date check | Wrong reporting cut-off or stale load |
| Format / schema check | Invalid datatype, length, enumeration or file structure |
| Control-total check | Truncation or packaging failure after upstream testing |

The final extract is a separate control point because downstream scripts, reporting tools and submission converters can contain logic not represented in the main ETL mapping. Validation should therefore compare back to governed upstream checkpoints rather than trusting that an earlier successful test remains valid after packaging.

### Where it sits

```text
Upstream:   Approved mapping · Tested data product · UAT
This:       Final extract and payload validation
Downstream: Regulatory production · Submission · Defect management
```

### Never confuse [Extract validation] and [Schema validation]

**Extract validation** - proves the content is the right population and values for the intended use.

---

**Schema validation** - proves the file conforms technically to a required structure. A perfectly valid file can contain the wrong numbers.

### Permanent rule

The artifact that leaves the bank or feeds the final report must be validated as an artifact in its own right.

### Permanent trap

Reconciling before the final reporting layer and assuming nothing can change afterwards. Late transformations, sign conventions, formatting or filters can introduce defects after upstream controls have passed.

### Jurisdiction variants

**No delta.** The validation mechanic is universal; technical schemas and submission formats vary by reporting estate.

<Recall
  q="Why can schema validation not replace content validation?"
  a="Schema checks confirm structure and permitted formats, not whether the extract contains the correct records, classifications, balances or reference date."
/>

<Recall
  q="What should a downstream extract reconcile to?"
  a="Controlled upstream checkpoints with the same defined scope and cut-off, adjusted only for documented transformations that belong in the final reporting layer."
/>
