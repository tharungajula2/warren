  Data leakage happens when a model’s training data inadvertently includes
  information that would not be available in practice at the time of prediction.
  This gives misleadingly good performance on training and validation, but fails

There are two main leakage types: *target leakage*, where predictors include the outcome itself (or its proxies), and *train-test contamination*, where observations in the test period influence training (e.g. shuffling time series). For example, if we include “*ever defaulted*” status (logged after six months) as an input to predict one-year default, the model essentially sees part of the answer. Another example: mixing borrowers from 2019 (test year) into 2018 training can let the model indirectly learn future trends.

To avoid leakage, ensure each feature is computable from information available at model decision time. In credit scoring, use only origination attributes or lagged variables. Rigorously align time: treat all data as of a cutoff date. For instance, if predicting default within a year, use only features known at loan issuance. Data pipelines should separate historical features from label construction. Finally, always evaluate on truly unseen data (see QNT-23) – a sharp drop from training to test performance is a red flag for leakage or overfitting.

<Rule label="PERMANENT RULE">
Never include any variable that cannot be known at scoring time. Ask, “Would this feature be available in real-time?” If not, omit or shift it.
</Rule>

<Trap label="PERMANENT TRAP">
Including any proxy of the target. For example, “balance after 1 year” to predict default in that year looks innocent but is label leakage. Also beware of merging data incorrectly (e.g. including post-default loan closure status).
</Trap>

<NeverConfuse a="Data leakage" b="Overfitting">
**Data leakage** — model sees future or target-related information in training, giving overly optimistic accuracy.
---
**Overfitting** — model is too complex for the signal in training data (but without artificial leaks). Both can cause test drop-offs, but leakage violates causality.
</NeverConfuse>

<Rule label="NO DELTA">
**No delta.** All jurisdictions expect no data leakage in model development. Regulatory model validation (e.g. AIRB guidance) specifically checks that feature timing is correct.
</Rule>
