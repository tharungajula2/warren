For example, joining a *Facility* table to its *Account* table: each facility (one side) may link to multiple accounts (many side). An inner join lists only facilities that have accounts, whereas a left join lists all facilities with matching accounts (NULL account fields if none). Beware of **fan-out**: joining a 1:M relationship will duplicate the "one" side row for each "many" side row, potentially inflating counts. Always ensure join keys are correct and understand cardinality.

```text
   +---------+      +---------+
   | Table A |      | Table B |
   +---------+      +---------+
         \         /
          \  JOIN /
           \     /
        +-----------+
        | Result    |
        +-----------+
```

### Permanent rule

Always specify an `ON` condition (join key) to match rows. For example: `ON Facilities.FacID = Accounts.FacID`.

### Permanent trap

Forgetting the join condition (or typo) leads to a Cartesian product (every A with every B). Also, joining on the wrong key can cause hidden duplicates (fan-out).

### Never confuse

**INNER JOIN** — returns only rows where keys match in both tables.

---

**CROSS JOIN** — returns Cartesian product (every row of A with every row of B), no key condition.

### Jurisdiction variants

**No delta.** JOIN semantics (INNER, LEFT, RIGHT, FULL) are standard SQL.
