### Core mechanism

```text
Source
    ↓
Extraction
    ↓
Cleaning / transformation
    ↓
Development dataset
    ↓
Model inputs
    ↓
Production feed
```

At every step ask: complete? accurate? timely? representative? reproducible? controlled?

| Data property | Validation question |
| :--- | :--- |
| Provenance | Where did the field originate? |
| Lineage | What transformations occurred before use? |
| Accuracy | Does the value represent what the model assumes it represents? |
| Completeness | Are missing observations understood and treated consistently? |
| Representativeness | Does development evidence reflect the intended population and conditions? |
| Stability | Has the distribution or meaning changed? |
| Consistency | Do development and production definitions match? |
| Access / retention | Can the evidence be reproduced and challenged later? |

Synthetic data does not remove these questions; it adds questions about generation logic, realism and whether synthetic patterns distort the relationship the model is meant to learn.

### Ownership

| Role | Responsibility |
| :--- | :--- |
| Data owner | Authoritative definitions and quality controls |
| Developer | Documents selection, transformations and exclusions |
| Model owner | Ensures production feed remains fit for use |
| Validation | Independently tests lineage, relevance and representativeness |

### Permanent rule

Data quality is purpose-dependent. The same dataset can be adequate for one model and inadequate for another because target population, horizon or required precision differ.

### Never confuse [Data accuracy] and [Data representativeness]

**Data accuracy** - recorded values correctly reflect the underlying observations.

---

**Data representativeness** - the observations collectively reflect the population and conditions for which the model will be used.

### Permanent trap

Treating a successful data-quality dashboard as proof of model-data suitability. Fields can be complete and internally consistent while the sample is stale, selected or irrelevant to the intended use.

### Jurisdiction variants

No delta. Data governance vocabulary varies, but traceability, quality, relevance and consistency between development and use are common model-development and validation expectations.

<Recall
  q="How can accurate data still create model risk?"
  a="The data may be non-representative, stale or drawn from a population unlike the intended use, so accurate observations can still support unreliable inference."
/>

<Recall
  q="Why must production lineage be compared with development lineage?"
  a="A model can be validated on one field definition or transformation and then receive a subtly different production feed, creating implementation and performance risk without changing code."
/>
