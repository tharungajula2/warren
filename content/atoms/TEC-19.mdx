### Core mechanism

A SQL extract can be loaded directly into a DataFrame:

```python
import pandas as pd

query = """
SELECT
    account_id,
    reporting_date,
    outstanding_balance,
    days_past_due,
    status
FROM loan_snapshots
WHERE reporting_date = '2026-08-31'
"""

loans = pd.read_sql(query, connection, parse_dates=["reporting_date"])
```

For a delivered CSV, specify the date fields and inspect inferred types rather than accepting them blindly:

```python
loans = pd.read_csv(
    "loan_snapshot_2026_08.csv",
    parse_dates=["reporting_date"]
)

print(loans.shape)
print(loans.dtypes)
```

Large files may need chunked processing rather than a single in-memory load. The useful question is not "Can pandas open it?" but whether the working set, intermediate merges, and copies fit comfortably enough to complete the analysis reproducibly.

Do not load identifiers as numbers when formatting matters. An account code such as `000123` can lose leading zeros if inferred as an integer. For file inputs, supply a string dtype for identifiers when necessary.

```python
loans = pd.read_csv(
    "loan_snapshot_2026_08.csv",
    dtype=&#123;"account_id": "string"&#125;,
    parse_dates=["reporting_date"]
)
```

### Permanent rule

Inspect row count, column names, dtypes, and date range immediately after loading before performing credit calculations.

### Never confuse [Identifier] and [Numeric measure]

**Identifier** - a label used to match records; arithmetic meaning is irrelevant and leading zeros may matter.

---

**Numeric measure** - a quantity such as balance or DPD on which arithmetic or ordering is meaningful.

### Permanent trap

Trusting dtype inference for every delivered file. Mixed values, blank cells, or formatted identifiers can produce object columns or altered keys that later break joins.
