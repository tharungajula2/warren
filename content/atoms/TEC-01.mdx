### Core mechanism

Use one mental schema throughout the pack:

```sql
SELECT account_id, reporting_date, outstanding_balance, days_past_due
FROM loan_snapshots
WHERE reporting_date = '2026-08-31';
```

Here `loan_snapshots` has grain **one row per account per reporting date**. The key is therefore `(account_id, reporting_date)`, not `account_id` alone. Other tables have different grains: `customers` is one row per customer; `facilities` is one row per facility; `loan_accounts` is one row per account; `repayment_schedule` is one row per account per due date; `payments` is one row per payment event identified by `payment_id`; `customer_risk` is one row per customer per effective-dated risk record. `finance_balances` is the comparison source used only for reconciliation, at account and reporting-date grain.

A key question comes before every calculation: if two rows share the business identifier, are they duplicates or legitimate repeated observations? Two `loan_snapshots` rows for the same account on different month-ends are expected. Two rows for the same account and same reporting date are a duplicate at the declared grain.

```sql
SELECT account_id, reporting_date, COUNT(*) AS row_count
FROM loan_snapshots
GROUP BY account_id, reporting_date
HAVING COUNT(*) &gt; 1;
```

The same logic protects monetary measures. If `outstanding_balance` is stored at account-month grain, any operation that changes that grain can change the total unless the transformation is deliberate.

### Permanent rule

State the grain in words before writing the query. A key is correct only relative to that grain.

### Never confuse [Duplicate] and [Repeated observation]

**Duplicate** - two or more rows occupy the same declared grain when only one should exist.

---

**Repeated observation** - the same entity appears legitimately at different dates, events, or child records.

### Permanent trap

Using `DISTINCT` to hide unexplained duplicates. It removes identical result rows but does not prove that the underlying grain or join is correct.

### Jurisdiction variants

No delta. Row grain and key logic do not vary by regulator.

<Recall
  q="What is the grain of a monthly loan snapshot table keyed by account and reporting date?"
  a="One row per account per reporting date; both columns are needed to identify a unique observation."

<Recall
