### Core mechanism

A uniqueness check for monthly snapshots tests the declared key:

```sql
SELECT
    account_id,
    reporting_date,
    COUNT(*) AS row_count
FROM loan_snapshots
GROUP BY account_id, reporting_date
HAVING COUNT(*) &gt; 1;
```

A mandatory-field rule returns records whose required value is absent:

```sql
SELECT account_id, reporting_date
FROM loan_snapshots
WHERE outstanding_balance IS NULL;
```

Referential integrity can be checked with an anti-join. This finds account records pointing to facilities that are absent:

```sql
SELECT a.account_id, a.facility_id
FROM loan_accounts a
LEFT JOIN facilities f
  ON f.facility_id = a.facility_id
WHERE f.facility_id IS NULL;
```

A domain check can detect impossible values supplied by the business rule:

```sql
SELECT account_id, reporting_date, days_past_due
FROM loan_snapshots
WHERE days_past_due &lt; 0;
```

The returned row count is not enough for investigation. Include the business key, reporting date, offending value, and where useful the rule identifier in the exception output so the result can be traced back to source data.

Do not label every repeated child record a duplicate. `payments` legitimately has many rows per account; the test must use the actual expected key, such as a payment identifier or another event-level key.

### Permanent rule

Translate each data-quality rule into a query whose zero or non-zero result has an unambiguous meaning at the declared grain.

### Never confuse [Business duplicate] and [Repeated child row]

**Business duplicate** - more than one row exists at a grain that should be unique.

---

**Repeated child row** - multiple rows are legitimate because the table grain is one row per event or schedule item.

### Permanent trap

Writing a DQ count without retaining exception keys. A failing count proves a problem exists but gives the investigator nothing to locate or repair.

### Jurisdiction variants

No delta. SQL implementation of DQ checks does not vary by regulator.

<Recall
  q="What determines the columns used in a duplicate check?"
  a="The declared grain of the table; the grouped columns must represent the key that should be unique at that grain."
/>

<Recall
  q="How do you find orphaned account-to-facility relationships?"
  a="Left join accounts to facilities and keep rows where the parent facility key is NULL after the join."
/>

<Recall
  q="Why should a DQ exception output contain business keys?"
  a="The analyst or data owner needs traceable records to investigate; an aggregate failure count alone is not actionable."
