### Core mechanism

Classify the incoming request before opening change control.

| Incoming item | Meaning | Treatment |
| :--- | :--- | :--- |
| Clarification | Same approved meaning, expressed more clearly | Update wording with traceable confirmation |
| Correction | Baseline inaccurately captured already-approved meaning | Correct with owner evidence |
| Scope change | Adds, removes or moves committed outcome | Impact assessment and approval |
| Requirement change | Alters behaviour, rule, boundary or acceptance condition | Impact assessment and approval |
| Design change | Alters solution while requirement remains stable | Solution governance; BA assesses business impact |
| Defect | Delivered behaviour fails agreed expectation | Defect process; release consequence assessed separately |

For a material change, assess effect before approval: mandate, requirements, design, data, testing, controls, dependencies, cost, schedule, readiness and evidence. The answer may be "no impact" for some dimensions, but it should be considered rather than assumed.

```text
Change request -&gt; Classify -&gt; Impact assess -&gt; Decision authority -&gt; Baseline/version update -&gt; Trace downstream effects
```

Never replace the prior baseline. Preserve what was approved, the approved change and which downstream artefacts must be revisited.

### Where it sits

```text
Upstream:   Signed baseline · New information · Design constraint · Policy decision
This:       Change classification · Impact · Approval · Version control
Downstream: Revised requirements · Delivery plan · Traceability · Evidence
```

### Ownership

| Role | Responsibility |
| :--- | :--- |
| Produces | BA documents business change and coordinates impact assessment |
| Approves | Scope or requirement authority approves within mandate |
| Consumes | Delivery, testing, governance and operations consume the revised baseline |
| Independently challenges | Risk or control functions challenge changes affecting their mandates |

### Permanent rule

A baseline is allowed to change; it is not allowed to change invisibly. Material changes require preserved history, assessed consequences and authorised approval.

### Never confuse [Scope change] and [Requirement clarification]

**Scope change** - changes what outcome or obligation is committed.

---

**Requirement clarification** - makes the existing approved meaning clearer without changing the obligation.

### Never confuse [Defect] and [Change request]

**Defect** - delivered behaviour fails an agreed requirement or expected result.

---

**Change request** - proposes a different requirement, scope or solution from the current approved baseline.

### Permanent trap

Calling a late request a "clarification" to avoid governance. If it changes expected behaviour, acceptance conditions, boundaries or constraints, it changes the baseline regardless of the label.

No delta.
