### Core mechanism

A common mistake is to transform a filtered column inside the predicate, which can make an otherwise usable index or partition less helpful. Prefer explicit date boundaries:

```sql
SELECT account_id, outstanding_balance
FROM loan_snapshots
WHERE reporting_date &gt;= '2026-08-01'
  AND reporting_date &lt; '2026-09-01';
```

Rather than selecting every column through every stage, carry only fields needed downstream:

```sql
WITH month_end AS (
    SELECT account_id, outstanding_balance, days_past_due
    FROM loan_snapshots
    WHERE reporting_date = '2026-08-31'
)
SELECT account_id, outstanding_balance
FROM month_end
WHERE days_past_due &gt; 0;
```

Execution plans reveal where the engine expects to spend work: scans, join methods, sorts, aggregations, and estimated row counts. If a join expects millions of rows where the business grain suggests thousands, first suspect cardinality or missing filters before asking for an index.

Performance has costs beyond elapsed time. Sorting for window functions can be expensive; `UNION` may need duplicate elimination; repeated CTE logic may be recalculated; wide `SELECT *` results move more data than necessary. Conversely, forcing premature micro-optimizations can make code unreadable without improving execution.

The analyst should understand the plan well enough to diagnose query shape, then involve database specialists for physical design decisions such as indexing, partitioning, statistics maintenance, and engine-specific configuration.

### Permanent rule

Optimize the amount of data processed before optimizing syntax: filter early, avoid accidental row multiplication, and inspect the plan.

### Never confuse [Logical correctness] and [Efficient execution]

**Logical correctness** - the query returns the intended population and measures.

---

**Efficient execution** - the engine produces that answer with acceptable scans, memory, sorting, and runtime.

### Permanent trap

Assuming an index is always the answer to a slow query. A wrong join grain or missing date filter can create far more work than any index can reasonably fix.
