### Core mechanism

A simple exposure calculation can operate directly on columns:

```python
portfolio["total_commitment"] = (
    portfolio["outstanding_balance"]
    + portfolio["undrawn_amount"].fillna(0)
)
```

Conditional bucketing can use `numpy.select` without a row-wise function:

```python
import numpy as np

conditions = [
    portfolio["days_past_due"].eq(0),
    portfolio["days_past_due"].between(1, 30),
    portfolio["days_past_due"].between(31, 89),
    portfolio["days_past_due"].ge(90),
]

choices = ["CURRENT", "DPD_1_30", "DPD_31_89", "DPD_90_PLUS"]

portfolio["dpd_bucket"] = np.select(
    conditions,
    choices,
    default="UNKNOWN",
)
```

Group-level quantities can often be returned to every row with `transform`:

```python
portfolio["customer_balance"] = (
    portfolio.groupby("customer_id")["outstanding_balance"]
    .transform("sum")
)
```

A Python loop or `DataFrame.apply(axis=1)` is not forbidden. It is appropriate when the logic genuinely depends on row-wise Python objects or cannot be expressed clearly with built-in operations. But using row-wise apply for ordinary arithmetic or simple conditions pays Python-call overhead once per row and often obscures the underlying rule.

Vectorized code can still be wrong. Missing values, dtype coercion, index alignment, and inconsistent units must be handled just as carefully as in any other calculation.

### Never confuse [Vectorization] and [Correctness]

**Vectorization** - expresses operations over arrays or Series efficiently.

---

**Correctness** - the calculation uses the right population, units, missing-value treatment, and business rule.

### Permanent rule

Prefer built-in column and group operations when they express the rule clearly; use row-wise Python only when the logic truly requires it.

### Permanent trap

Replacing every loop with dense vectorized code that nobody can review. Performance gains do not justify hiding the business rule in unreadable expressions.
