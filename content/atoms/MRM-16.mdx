### Core mechanism

| Workstream | Validator's question |
| :--- | :--- |
| Purpose and use | Is the model solving the stated problem and being judged against the right criteria? |
| Conceptual soundness | Are methodology, assumptions and judgement defensible? |
| Data | Are sources, transformations and populations fit for use? |
| Implementation | Does executable production logic match approved design? |
| Development evidence | Were tests sufficiently demanding and transparent? |
| Outcomes | Does realised evidence support ranking, levels and predictions? |
| Stability | Have population or relationships moved? |
| Benchmarking | Does an independent comparator reveal weakness? |
| Limitations | Are weaknesses explicit, bounded and controlled? |
| Use | Are users operating within approved scope? |

```text
Scope
    ↓
Review developer evidence
    ↓
Reperform / independently test where warranted
    ↓
Challenge assumptions and use
    ↓
Synthesize evidence
    ↓
Findings and validation opinion
```

Validation is not a checklist where strong performance on one dimension cancels a fundamental failure on another. High discrimination, for example, cannot make corrupted data or unauthorised use acceptable.

### Where it sits

```text
Upstream:   Validation mandate · Development evidence
This:       End-to-end validation programme
Downstream: Outcomes analysis · Stability / benchmarking · Validation findings
```

### Ownership

| Role | Responsibility |
| :--- | :--- |
| Validation lead | Sets risk-based scope and conclusion |
| Specialist validators | Perform technical and data challenge |
| Model owner | Supplies complete evidence and responds to challenge |
| Business user | Explains actual use and limitations in practice |

### Permanent rule

Validation evaluates the model as a used decision system, not only as a mathematical object.

### Never confuse [Validation scope] and [Validation checklist]

**Validation scope** - risk-based set of questions and tests needed to support a conclusion on the specific model.

---

**Validation checklist** - control aid that can promote consistency but cannot decide which evidence is materially important.

### Permanent trap

Declaring a model valid because every standard template field is complete. Documentation completeness is evidence of governance, not proof that the model is conceptually or empirically reliable.

### Jurisdiction variants

No delta. The exact depth varies with model type and materiality, but conceptual soundness, data, implementation, performance, limitations and use are common dimensions of robust validation.

<Recall
  q="Why should validation examine actual model use?"
  a="A technically sound model can still generate model risk when users apply it outside the population, decision or conditions supported by the evidence."
/>

<Recall
  q="Can strong performance metrics compensate for a conceptual flaw?"
  a="No. Metrics are one evidence stream; a fundamental data, design or use failure can remain material even when historical performance looks strong."
/>
