### Core mechanism

A monthly account snapshot joined directly to a repayment schedule is a classic fan-out risk. One account-month row can match many scheduled instalments:

```sql
SELECT
    s.account_id,
    s.reporting_date,
    s.outstanding_balance,
    r.due_date,
    r.scheduled_amount
FROM loan_snapshots s
JOIN repayment_schedule r
  ON r.account_id = s.account_id
WHERE s.reporting_date = '2026-08-31';
```

If account `A100` has one snapshot row and twelve schedule rows, its August balance appears twelve times. A later `SUM(outstanding_balance)` is then twelve times too large even though every join key technically matched.

Diagnose cardinality before trusting measures:

```sql
SELECT
    s.account_id,
    COUNT(*) AS joined_rows
FROM loan_snapshots s
JOIN repayment_schedule r
  ON r.account_id = s.account_id
WHERE s.reporting_date = '2026-08-31'
GROUP BY s.account_id
HAVING COUNT(*) &gt; 1;
```

The safe shape depends on the intended result grain. If the output must remain one row per account-month, first reduce the schedule to one row per account for the required period, then join that result. A one-to-many relationship is not inherently wrong; it is wrong when the output grain was supposed to stay on the one side.

Many-to-many joins are more dangerous because both sides contain repeated join keys. They can multiply rows combinatorially and often indicate that the join condition is incomplete or that one or both inputs need aggregation first.

### Permanent rule

Predict result cardinality before joining, then verify row counts and key uniqueness after the join.

### Never confuse [Valid one-to-many join] and [Fan-out error]

**Valid one-to-many join** - repeated rows are required because the target grain is on the many side.

---

**Fan-out error** - repeated rows were created even though the target grain was supposed to remain on the one side.

### Permanent trap

Checking only whether the join returned the expected accounts. All accounts can be present while balances are silently multiplied.

### Jurisdiction variants

No delta. Join cardinality does not vary by regulator.

<Recall
  q="Why can joining one snapshot row to twelve schedule rows inflate exposure?"
  a="The snapshot balance is repeated once for every matching schedule row, so any later sum counts the same balance twelve times."
/>

<Recall
  q="Is every one-to-many join wrong?"
  a="No. It is correct when the target result genuinely has one row per child record; it is a problem only when the intended grain should remain on the parent side."
/>

<Recall
  q="What should be checked immediately after a risky join?"
  a="Recheck row count, uniqueness at the intended key, and controlled monetary totals against the pre-join population."
/>
