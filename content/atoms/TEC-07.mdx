### Core mechanism

For an August account-level portfolio, `loan_snapshots` is the base. `loan_accounts`, `facilities`, and `customers` are one-row lookups along the account-to-facility-to-customer path:

```sql
SELECT
    s.account_id,
    f.facility_id,
    c.customer_id,
    c.segment,
    f.product_type,
    s.outstanding_balance,
    s.days_past_due
FROM loan_snapshots s
JOIN loan_accounts a
  ON a.account_id = s.account_id
JOIN facilities f
  ON f.facility_id = a.facility_id
JOIN customers c
  ON c.customer_id = f.customer_id
WHERE s.reporting_date = '2026-08-31';
```

Now suppose the output also needs scheduled cash due during September. The raw schedule is many rows per account, so first reduce it to account grain:

```sql
WITH september_due AS (
    SELECT
        account_id,
        SUM(scheduled_amount) AS scheduled_amount_sep
    FROM repayment_schedule
    WHERE due_date &gt;= '2026-09-01'
      AND due_date &lt; '2026-10-01'
    GROUP BY account_id
)
SELECT
    s.account_id,
    s.outstanding_balance,
    d.scheduled_amount_sep
FROM loan_snapshots s
LEFT JOIN september_due d
  ON d.account_id = s.account_id
WHERE s.reporting_date = '2026-08-31';
```

The `LEFT JOIN` keeps all August accounts even when no September schedule exists. The pre-aggregation ensures at most one schedule row can match each account.

After the join, validate the intended account-month key and a control total. Those checks belong in the analyst query or test harness rather than in memory.

### Never confuse [INNER JOIN] and [LEFT JOIN]

**INNER JOIN** - keeps only base rows with a matching row on the other side.

---

**LEFT JOIN** - keeps every base row and supplies NULLs when no right-side match exists.

### Permanent rule

Choose the base table from the desired output grain and force every many-side input to the required matching grain before joining.

### Permanent trap

Starting from whichever table is easiest to type. The starting grain determines what can be duplicated or lost later.

  a="The schedule has multiple rows per account; aggregation creates one matching row per account and prevents the snapshot balance from being repeated."
