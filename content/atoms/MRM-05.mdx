### Core mechanism

| Inventory field | Control question |
| :--- | :--- |
| Model ID/version | Exact governed object? |
| Purpose/use | Which decision depends on it? |
| Owner/user | Who is accountable/consumes output? |
| Risk tier | Required control intensity? |
| Status | Development, validation, active, restricted, inactive or retired? |
| Validation/approval | Authorised, with what conditions? |
| Upstream dependencies | What can contaminate it? |
| Downstream consumers | What fails if it fails? |
| Third-party status | External dependency? |
| Limitations/issues | Known open weaknesses? |

Model A data → Model B estimate → Model C decision output

Dependency mapping links inventory rows into chains, exposing propagation when upstream failure contaminates downstream models.

### Where it sits

```text
Upstream:   Model perimeter · Ownership · Lifecycle states
This:       Inventory and dependency map
Downstream: Tiering · Aggregate risk · Validation scheduling · Change impact
```

### Ownership

| Role | Responsibility |
| :--- | :--- |
| Model owner | Keeps model record accurate |
| Business / technology | Confirms actual use and dependencies |
| MRM function | Sets inventory standards and challenges completeness |
| Internal audit | Tests completeness and reconciliation |

### Permanent rule

One model has one governed identity, but it may have many uses, versions and dependencies. Inventory controls must preserve that distinction.

### Never confuse [Model inventory] and [Model repository]

**Model inventory** - authoritative governance record showing models, status, ownership and control attributes.

---

**Model repository** - storage location for code, documentation, artefacts or files; it may support the inventory but does not replace it.

### Permanent trap

Keeping retired or restricted models invisible. Historical lineage matters for reproducing past decisions, understanding inherited outputs and managing transitions.

### Jurisdiction variants

| Jurisdiction | Inventory expectation | Scope / status |
| :--- | :--- | :--- |
| US | Risk-based identification sufficient for individual and aggregate model-risk oversight; no fixed template. | 2026 guidance less prescriptive than predecessor. |
| UK | SS1/23 Principle 1: identify models, maintain inventory, classify risk for proportionate controls. | Formal inventory expectation. |
| EU | CRR/ECB governs prudential model scope, rating systems, changes and permissions. | No enterprise inventory mandate for every quantitative tool. |
| IN | Proposed current inventory covering active, inactive, decommissioned, third-party and AI/ML models. | Draft as at August 2026; not final. |

<Recall
  q="Why is a dependency map more useful than a flat list?"
  a="It reveals propagation risk: a common upstream dataset, model or service can impair several downstream models and decisions simultaneously."
/>

<Recall
  q="What makes an inventory authoritative?"
  a="It has governed identifiers, owners, lifecycle and control status, is reconciled to actual use, and is updated when models or dependencies change."
/>
