### Core mechanism

| Defect field | Why it matters |
| :--- | :--- |
| Observed vs expected | States the failure objectively |
| Requirement / mapping link | Identifies intended behaviour |
| Severity and impact | Determines release and escalation consequence |
| Root cause | Distinguishes requirement, data, code or environment failure |
| Fix version | Identifies what changed |
| Retest evidence | Proves the original failure is removed |
| Regression impact | Proves the fix did not break adjacent logic |
| Closure authority | Prevents self-declared completion |

```text
Test or UAT failure
    ↓
Log and triage defect
    ↓
Assess severity and affected requirements
    ↓
Fix or formally disposition
    ↓
Retest original scenario
    ↓
Run affected regression scope
    ↓
Close with evidence or escalate
```

Severity is based on impact, not development effort. A one-line mapping error can be critical if it contaminates a regulatory population; a complex cosmetic defect may be low severity.

### Where it sits

```text
Upstream:   Test packs · UAT · Extract validation
This:       Delivery defect lifecycle
Downstream: Release decision · Enterprise issue management · Production readiness
```

### Never confuse [Defect] and [Data issue]

**Defect** - a failure of delivered behaviour against an approved requirement or expected result during change delivery.

---

**Data issue** - a broader governed weakness in live enterprise data or controls. A defect can reveal or become a data issue when the cause extends beyond the change.

### Permanent rule

A fix is not closed until the failed scenario passes and the relevant regression scope remains sound.

### Permanent trap

Closing a defect because the developer cannot reproduce it. The correct next step is evidence-based triage of data, environment and scenario conditions, not deletion of the problem.

### Jurisdiction variants

**No delta.** Defect mechanics are delivery controls and do not change by jurisdiction.

<Recall
  q="Why is retest alone insufficient after a fix?"
  a="The fix may solve the original case while breaking adjacent logic; regression testing checks the affected wider behaviour."
/>

<Recall
  q="When should a delivery defect enter enterprise issue management?"
  a="When it reveals a live, material or systemic weakness whose scope or remediation extends beyond the delivery release."
