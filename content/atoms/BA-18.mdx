Before decommissioning legacy processes, banks often run *both* systems in parallel to ensure the new one works correctly. For example, a bank might process a day’s transactions in both the old system and the new IFRS-compliant system and compare the results.  This parallel run period (sometimes months) builds confidence and provides audit evidence that the new outputs are accurate. It also allows real data to exercise the system without immediate risk.

The *go-live plan* (cutover plan) is executed once parallel runs are complete. It is a detailed schedule: which data migration steps to perform, which systems to shut down/start up, and who is responsible for each action.  The plan must include *rollback procedures*: if a critical issue occurs, how to revert to the old system to prevent business impact. For example, ensure backups and change logs are ready. Roles (executive sponsor, IT lead, BA, etc.) must be assigned for go/no-go decisions and communication to stakeholders.

### Permanent rule

Include parallel running and dual-reporting as part of implementation. Plan go-live steps meticulously and always have a tested rollback strategy. Confirm decision criteria (e.g. “all parallel outputs match 99%”) before full cutover.

### Permanent trap

Assuming go-live will succeed without rehearsal. A frequent mistake is not planning for failures – e.g. no rollback or contingency plan. Also failing to run both systems long enough to catch issues.

### Never confuse

**Parallel Run** vs **Dual Reporting**:
A *Parallel Run* is running old and new systems at the same time to validate output. *Dual Reporting* is submitting reports in both old and new regimes (e.g. old accounting vs new) to regulators. They both involve duplication but serve different verification purposes.

### No delta

These deployment practices are standard in banking globally, especially for compliance transitions.
