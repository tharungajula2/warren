### Core mechanism

| Requirement dimension | Question to resolve |
| :--- | :--- |
| Business meaning | What exactly does the item represent, including inclusions and exclusions? |
| Grain | One row per what: account, facility, trade, customer, legal entity or aggregate? |
| Population | Which products, entities, statuses, dates and geographies are in scope? |
| Source intent | What type of authoritative information is required? |
| Transformation | What filters, joins, classifications or derivations are required? |
| Timing | What reference date, cut-off, frequency and history apply? |
| Controls | What validations, reconciliations and evidence are required? |
| Acceptance | What observable result proves the requirement is satisfied? |

```text
Regulation or business need
    ↓
Clarify meaning, scope and grain
    ↓
Define data and control requirements
    ↓
Resolve assumptions and conflicts
    ↓
Write testable acceptance criteria
    ↓
Baseline and trace through delivery
```

Acceptance criteria should state the expected outcome, not merely "UAT successful". A requirement for a counterparty country field might specify the governed definition, source authority, applicable code set, null treatment and reconciliation expectation.

### Ownership

| Role | Delivery responsibility |
| :--- | :--- |
| BA / requirements lead | Elicits, resolves and documents testable need |
| Data owner | Approves governed meaning and material requirements |
| Producer / technology | Confirms implementability and source constraints |
| Consumer | Confirms the requirement supports intended use |
| Challenge / control | Tests whether control obligations are captured |

### Permanent rule

If a requirement cannot be objectively tested, it is not yet sufficiently specified for controlled delivery.

### Permanent trap

Copying a regulatory label into a BRD and treating it as a definition. Regulatory terms still need scope, grain, source interpretation and handling rules before implementation.

### Jurisdiction variants

**No delta.** The BA method is universal; the underlying regulatory requirement can differ by jurisdiction.

<Recall
  q="Why is grain a first-class requirement?"
  a="It determines keys, joins, aggregation and duplicate logic; two teams can implement the same field name differently if one assumes account grain and another customer grain."
/>

<Recall
  q="What makes an acceptance criterion useful?"
  a="It states an observable pass condition tied to the requirement, enabling testing and sign-off without relying on subjective statements such as &quot;looks correct&quot;."
