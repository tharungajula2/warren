For data migrations or integration, a **Data Mapping Specification** lists every data element to be transferred. Each row typically has: source table/field, source data type, target table/field, target data type, and *Transformation Logic/Business Rules*.  For example, a mapping might say `SRC.CUST_ID (VARCHAR)` maps to `CUST.ACCOUNT_NUMBER (String)` with rule “pad with leading zeros to length 15”. Or “DOB (YYYYMMDD) → Birthdate (YYYY-MM-DD)” to reformat dates.

This document serves as the *golden source* for developers and testers to implement and verify data flow. In banking, precise mapping is critical (e.g. for customer data, transactions). Missing a transformation can lead to errors or compliance issues.

<Rule label="PERMANENT RULE">
Document every data element and its transformation explicitly. Include data types and any business rule (e.g. code-to-description mapping) for each field.
</Rule>

<Trap label="PERMANENT TRAP">
Assuming simple copy (source to target) for all fields. Some fields require non-trivial transformation (format changes, code mappings) which must be written down, or testers cannot verify correctness.
</Trap>

<NeverConfuse>
**Source Field** vs **Target Field** in mapping:
A *Source Field* is the field in the existing (origin) system. A *Target Field* is where it goes in the new system.  Keep straight which is which when writing the spec.
</NeverConfuse>

### No delta

Data mapping documentation is the same process in any country or system. The need for clear source-to-target definitions is universal.

<Recall
  q="What is included in a data mapping spec?"
  a="Each source field, target field, types, and transformation (e.g. “convert code X→Y or reformat date”)."
/>

<Recall
  q="Why is a data mapping spec needed?"
  a="It’s the blueprint for data migration/integration, ensuring all data is correctly moved and transformed."
