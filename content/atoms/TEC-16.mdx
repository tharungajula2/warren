### Core mechanism

Assume `loan_snapshots` must reconcile to a delivered table `finance_balances` at account and reporting-date grain. Start by aggregating both sides to the same key before comparing:

```sql
WITH risk_side AS (
    SELECT
        account_id,
        reporting_date,
        SUM(outstanding_balance) AS balance
    FROM loan_snapshots
    WHERE reporting_date = '2026-08-31'
    GROUP BY account_id, reporting_date
),
finance_side AS (
    SELECT
        account_id,
        reporting_date,
        SUM(balance_amount) AS balance
    FROM finance_balances
    WHERE reporting_date = '2026-08-31'
    GROUP BY account_id, reporting_date
)
SELECT
    COALESCE(r.account_id, f.account_id) AS account_id,
    r.balance AS risk_balance,
    f.balance AS finance_balance,
    COALESCE(r.balance, 0) - COALESCE(f.balance, 0) AS difference
FROM risk_side r
FULL OUTER JOIN finance_side f
  ON f.account_id = r.account_id
 AND f.reporting_date = r.reporting_date
WHERE r.account_id IS NULL
   OR f.account_id IS NULL
   OR ABS(r.balance - f.balance) &gt; 1.00;
```

The full outer join exposes three exception classes: only on the risk side, only on the finance side, or present on both with a measure difference. The tolerance `1.00` is assumed to come from the control specification; TEC does not invent it.

Always reconcile counts as well as amounts. Equal totals can hide offsetting record-level errors, while equal record counts can hide value differences. Where currencies differ, align currency treatment before comparison rather than relying on a single net total.

### Where it sits

```text
Upstream:   Control specification · Aligned grain · Source populations
This:       Side-by-side comparison · Missing records · Amount differences
Downstream: Exception investigation · Control evidence · Reporting sign-off
```

### Permanent rule

Force both sides to the same key and measure definition before comparing them.

### Never confuse [Reconciliation specification] and [Reconciliation query]

**Reconciliation specification** - defines what must agree, the grain, measures, tolerance, and control expectation.

---

**Reconciliation query** - implements that definition and emits the exceptions or evidence.

### Permanent trap

Comparing only grand totals. Two sources can have the same net balance while containing different accounts or offsetting errors.

### Jurisdiction variants

No delta. Reconciliation SQL mechanics do not vary by regulator.

<Recall
  q="Why aggregate both sides before a reconciliation join?"
  a="The comparison is meaningful only when both sides are at the same declared grain; otherwise repeated records can create false differences or false matches."
/>

<Recall
  q="What are the three basic exceptions from a full outer reconciliation?"
  a="A record exists only on the first side, only on the second side, or exists on both sides but has a measure outside the specified tolerance."
/>

<Recall
  q="Why reconcile counts as well as balances?"
  a="Equal balances can arise from offsetting errors, so population-level agreement is not proved by a single monetary total."
