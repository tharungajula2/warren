### Core mechanism

| Test layer | What it proves | Typical evidence |
| :--- | :--- | :--- |
| Field logic | Transformation implements the mapping | Known input -&gt; expected target value |
| Population | Inclusion and exclusion rules work | In-scope and out-of-scope records |
| Boundary | Thresholds, dates and edge conditions behave correctly | Values immediately around cut-offs |
| Negative | Invalid or missing data is controlled | Rejection, exception or governed default |
| Reconciliation | Aggregates and populations remain complete | Source-to-target counts and balances |
| Regression | Existing behaviour not intended to change still works | Prior scenarios rerun after change |

```text
Requirement and mapping
    ↓
Identify risks of wrong implementation
    ↓
Design scenarios and expected results
    ↓
Prepare controlled test data
    ↓
Execute and capture evidence
    ↓
Defect or pass conclusion linked to requirement
```

Expected results should be calculated independently where practical. Repeating the developer's transformation in the test script can reproduce the same logic error and create false assurance.

### Where it sits

```text
Upstream:   Requirements · Mapping · Build output
This:       Test strategy and test packs
Downstream: Defects · UAT · Regression evidence · Release decision
```

### Ownership

| Role | Test responsibility |
| :--- | :--- |
| BA / test analyst | Designs scenarios from requirements and mappings |
| Developer | Performs technical testing and fixes defects |
| Business consumer | Confirms business scenarios and expected outcomes |
| Data owner | Ensures material CDE and control coverage |
| Challenge / control | Reviews adequacy where independent assurance is required |

### Permanent rule

Test coverage follows the risk of being wrong, not the number of fields changed.

### Permanent trap

Testing only happy-path records. Reporting defects frequently occur at nulls, effective-date boundaries, joins, duplicated keys, unusual classifications and exception handling.

### Jurisdiction variants

**No delta.** The testing method is universal; jurisdiction-specific rules simply create different scenarios and expected outcomes.

<Recall
  q="Why should expected results be independently derived where possible?"
  a="Reusing the production logic in the test can copy the same defect into both sides of the comparison, making an incorrect implementation appear to pass."
/>

<Recall
  q="What does regression testing protect?"
  a="It checks that changes intended for one requirement have not unintentionally altered existing mappings, populations, controls or downstream reports."
/>
