### Core mechanism

A DPD bucket can be implemented directly from `days_past_due`:

```sql
SELECT
    account_id,
    days_past_due,
    CASE
        WHEN days_past_due IS NULL THEN 'UNKNOWN'
        WHEN days_past_due = 0 THEN 'CURRENT'
        WHEN days_past_due BETWEEN 1 AND 30 THEN 'DPD_1_30'
        WHEN days_past_due BETWEEN 31 AND 60 THEN 'DPD_31_60'
        WHEN days_past_due BETWEEN 61 AND 89 THEN 'DPD_61_89'
        ELSE 'DPD_90_PLUS'
    END AS dpd_bucket
FROM loan_snapshots
WHERE reporting_date = '2026-08-31';
```

`CASE` is evaluated top to bottom. The first matching branch wins, so overlapping ranges can silently misclassify rows. Put exceptional states such as NULL first when they need their own treatment, then use non-overlapping conditions.

A searched `CASE` can also encode flags used later in aggregation:

```sql
SELECT
    account_id,
    CASE WHEN days_past_due &gt; 0 THEN 1 ELSE 0 END AS arrears_flag,
    CASE WHEN outstanding_balance &gt;= 1000000 THEN 1 ELSE 0 END AS large_exposure_flag
FROM loan_snapshots
WHERE reporting_date = '2026-08-31';
```

The code owns implementation, not policy. TEC can express `days_past_due &gt;= threshold`, but the threshold itself must come from the credit, impairment, capital, reporting, or jurisdiction-specific rule that owns it.

### Permanent rule

Make `CASE` branches mutually exclusive and collectively explicit for the values that matter, including NULL when it has business meaning.

### Never confuse [CASE rule] and [Business rule]

**CASE rule** - the SQL expression that implements a condition.

---

**Business rule** - the governed definition that determines what the condition should be.

### Permanent trap

Using `ELSE` as a silent garbage bucket. If unmatched values are possible and important, label them visibly so bad source values do not masquerade as a valid final category.

### Jurisdiction variants

No delta. `CASE` mechanics do not vary by regulator.
