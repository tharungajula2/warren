  A data dictionary is a detailed catalog of all fields (data elements),
  describing each one’s attributes (name, type, description, format, valid
  values, etc.). A data model (conceptual or logical) is a diagram showing
  entities and relationships between them. Together they help design systems and
  prevent misinterpretation.

For instance, in a bank’s credit risk data model, entities might include `Customer`, `Loan`, `Collateral`. The data dictionary would list that `Loan.Amount` is a numeric field in rupees, defined as “principal outstanding.” The dictionary is a repository of these definitions for technical staff, while the model visualizes how `Loan` relates to `Customer` and `Collateral`.

Having a data model ensures database tables and fields align with business concepts (avoids missing fields). The dictionary ensures anyone writing queries or reports knows exactly what each field means. Both should be version-controlled. When regulations introduce new report items, the dictionary/model must be updated. Without them, even a simple mapping exercise is error-prone, and data integration between systems becomes guesswork.

<Rule label="PERMANENT RULE">
Every data field in any regulatory report or risk system must be defined in the data dictionary and accounted for in the data model.
</Rule>

<Trap label="PERMANENT TRAP">
Skipping the dictionary for “obvious” fields; even basic terms like “balance” need precise definition in a banking context.
</Trap>

<NeverConfuse a="Data dictionary" b="Data catalog">
**Data dictionary** — A detailed list of fields and technical specs for developers and analysts.  
---  
**Data catalog** — A broader inventory (often tool-based) that may include the data dictionary and also lineage, quality metrics, etc.
</NeverConfuse>

<Rule label="NO DELTA">
**No delta.** The use of data dictionaries and models is a technical practice not dictated by law; best practices are common globally.
</Rule>

<Recall
