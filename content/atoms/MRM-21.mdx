### Core mechanism

```text
Approved version
    ↓
Production replication test
    ↓
Controlled release
    ↓
User applies model within approved scope
    ↓
Output accepted or overridden
    ↓
Decision + reason captured
    ↓
Override and use patterns monitored
```

| Use control | Question |
| :--- | :--- |
| Production reconciliation | Does live output match the approved implementation? |
| Access | Who can run or alter the model? |
| User guidance | Do users understand output, assumptions and limitations? |
| Scope controls | Can prohibited uses be prevented or detected? |
| Override authority | Who can depart from model output? |
| Reason codes | Why was the override made? |
| Outcome tracking | Did overrides improve or worsen decisions? |
| Usage evidence | Is the model actually used where governance assumes it is? |

Overrides are not inherently bad. Expert judgement can correct a known model limitation or incorporate information unavailable to the model. Risk rises when overrides are frequent, one-directional, poorly documented or concentrated by user or segment.

### Where it sits

```text
Upstream:   Approval conditions · Approved implementation
This:       Production use and overrides
Downstream: Monitoring · Issue escalation · Change management
```

### Ownership

| Role | Responsibility |
| :--- | :--- |
| Technology | Deploys the approved version and protects release controls |
| Business user | Uses output within scope and documents overrides |
| Model owner | Monitors usage and override patterns |
| MRM / validation | Challenges misuse and systematic override behaviour |

### Permanent rule

A manual override changes the decision, not the model. If repeated overrides reveal structural weakness, fix or restrict the model rather than normalising permanent manual correction.

### Never confuse [Override] and [Model adjustment]

**Override** - case-specific human decision that departs from model output.

---

**Model adjustment** - systematic change to model output, logic or post-model treatment applied across defined cases and governed as model change or mitigation.

### Permanent trap

Monitoring only override frequency. Ten justified overrides can be healthier than two undocumented ones; direction, reason, user concentration and realised outcome matter.

### Jurisdiction variants

No delta. The use-control mechanism is universal even though particular sectors or models may have separate use-test or approval requirements.

<Recall
  q="When do overrides become evidence of model risk?"
  a="When their frequency, direction or reasons show that users repeatedly correct the same model weakness or no longer trust the output, especially if outcomes confirm the pattern."
/>

<Recall
  q="Why must deployment be reconciled to the approved version?"
  a="Validation and approval attach to a specific implementation. A production difference in code, transformation or configuration can create an effectively unvalidated model."
/>
