For example, on an *Exposure* table, one might retrieve loan amounts and borrower IDs for high-risk loans:  
```sql
SELECT LoanID, Principal, BorrowerID
FROM Exposures
WHERE RiskRating = 'High'
ORDER BY Principal DESC;
```  
Here `SELECT LoanID, Principal, BorrowerID` picks columns, `WHERE RiskRating = 'High'` filters rows to high-risk ones, and `ORDER BY Principal DESC` sorts the resulting loans by size (largest first).

The `WHERE` clause applies conditions (e.g. numerical comparisons, string matches) to each row; only rows meeting all conditions appear in the result. After filtering, `ORDER BY` arranges the rows by one or more columns. Without `ORDER BY`, SQL does not guarantee any specific row order.

<Rule label="PERMANENT RULE">
If a specific ordering is needed, always include an `ORDER BY` clause. By default, results are unordered.
</Rule>

<Trap label="PERMANENT TRAP">
Omitting a `WHERE` filter can return huge result sets. Ensure conditions are correct; unintended broad filters (e.g. `WHERE 1=1`) can slow the query and return irrelevant data.
</Trap>

<NeverConfuse a="WHERE" b="ORDER BY">
**WHERE** — filters rows before grouping or sorting (applies to individual rows).  
---  
**ORDER BY** — sorts the final result rows (after filtering).
</NeverConfuse>

<Rule label="NO DELTA">
**No delta.** The semantics of `SELECT`, `WHERE`, and `ORDER BY` are standard SQL across jurisdictions.
</Rule>
