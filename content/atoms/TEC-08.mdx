### Core mechanism

The simplest correct month-end query fixes one reporting date before any enrichment or aggregation:

```sql
SELECT
    account_id,
    outstanding_balance,
    undrawn_amount,
    days_past_due,
    status
FROM loan_snapshots
WHERE reporting_date = '2026-08-31';
```

If the source can contain multiple intra-month dates but the task needs the latest observation in each month, derive that selection deliberately rather than assuming the calendar maximum exists for every account. One common shape is to rank observations within account and month:

```sql
WITH ranked AS (
    SELECT
        account_id,
        reporting_date,
        outstanding_balance,
        ROW_NUMBER() OVER (
            PARTITION BY account_id,
                         EXTRACT(YEAR FROM reporting_date),
                         EXTRACT(MONTH FROM reporting_date)
            ORDER BY reporting_date DESC
        ) AS rn
    FROM loan_snapshots
)
SELECT account_id, reporting_date, outstanding_balance
FROM ranked
WHERE rn = 1;
```

That pattern selects the latest available observation per account-month, which is different from demanding a specific contractual month-end. The business requirement must say which one is intended.

Point-in-time correctness also means every attached attribute must be valid for the same observation date. Joining an August snapshot to the customer's current risk grade in a table that has since changed introduces future information into historical analysis.

### Where it sits

```text
Upstream:   Snapshot grain · Reporting date requirement
This:       Observation-date selection · Month-end population
Downstream: As-of joins · Delinquency history · Vintage analysis
```

### Never confuse [Calendar month-end] and [Latest available observation]

**Calendar month-end** - a specifically required reporting date such as 31 August.

---

**Latest available observation** - the maximum date present for the account or period, which may be earlier or later than the contractual cut-off.

### Permanent rule

Every point-in-time portfolio must have one explicit observation rule, and all later attributes must be aligned to that observation.

### Permanent trap

Using `MAX(reporting_date)` over the whole table and calling the result month-end. It returns the latest date present globally, not necessarily the required cut-off for every account.

### Jurisdiction variants

No delta. Point-in-time query mechanics do not vary by regulator.

  q="Why is a snapshot table not safe to aggregate without a date filter?"
  a="The same account appears at multiple reporting dates, so balances from different periods would be summed together."

<Recall
  q="What is the difference between a required month-end and the latest available row?"
  a="A required month-end is a defined cut-off; the latest available row is merely the newest observation present and may not represent that cut-off."
