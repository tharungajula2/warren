### Core mechanism

```text
Purpose + data constraints
    ↓
Candidate methods
    ↓
Assumptions and trade-offs
    ↓
Chosen method
    ↓
Complexity justified by incremental value
    ↓
Documented limitations and tests
```

| Question | Evidence expected |
| :--- | :--- |
| Why this method? | Link to purpose, output and decision need |
| What assumptions matter? | Explicit assumptions and conditions under which they fail |
| What alternatives were considered? | Comparison sufficient to show selection was reasoned |
| What does complexity add? | Better performance, stability, flexibility or decision usefulness |
| What does complexity cost? | Explainability, data dependence, implementation and validation burden |
| Where is judgement embedded? | Variable choices, segmentation, constraints, overrides or expert assumptions |

A more complex model is not inherently superior. Complexity increases the number of ways assumptions, interactions, implementation and user understanding can fail.

### Where it sits

```text
Upstream:   Purpose · Data fitness · Business constraints
This:       Method, assumptions and complexity
Downstream: Implementation · Developer testing · Conceptual validation
```

### Ownership

| Role | Responsibility |
| :--- | :--- |
| Developer | Selects and documents method and assumptions |
| Model owner | Accepts design rationale for intended use |
| Business user | Provides practical context and challenges implausible behaviour |
| Validation | Independently challenges conceptual soundness |

### Permanent rule

Complexity must be justified by useful model capability, not by technical sophistication alone.

### Never confuse [Assumption] and [Parameter]

**Assumption** - proposition or simplification the model relies on, such as stability of a relationship or suitability of a data treatment.

---

**Parameter** - estimated or set quantity within the chosen model structure. Updating a parameter does not necessarily repair a broken assumption.

### Permanent trap

Using strong historical fit as proof of conceptual soundness. A misspecified or over-complex model can fit development data very well while relying on unstable or spurious relationships.

### Jurisdiction variants

No delta. The technical methods vary by model, but regulators consistently expect methodology, assumptions and judgement to be documented, challenged and proportionate to use and materiality.

<Recall
  q="When does extra model complexity become model risk rather than model improvement?"
  a="When it adds assumptions, opacity or implementation burden without commensurate evidence that it improves the decision the model supports."
/>

<Recall
  q="Why can recalibrating parameters fail to repair an assumption problem?"
  a="Recalibration changes quantities inside the existing structure; if the underlying relationship or structural assumption is no longer valid, the model form itself may need redevelopment."
/>
