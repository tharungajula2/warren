### Core mechanism

| Intervention | What changes | Appropriate when | Control question |
| :--- | :--- | :--- | :--- |
| Correction | Code, data mapping or implementation | Approved design was implemented wrongly | Was the defect removed and retested? |
| Overlay / adjustment | Output outside the core model | Temporary limitation needs mitigation | Is scope and removal criterion controlled? |
| Recalibration | Parameters or level alignment | Structure remains sound but levels drifted | Does evidence support retaining the model form? |
| Redevelopment | Variables, architecture, method or core assumptions | Structural weakness or new purpose makes the old model inadequate | Is this effectively a new model? |

```text
Monitoring / finding
    ↓
Root cause
    ↓
Change classification
    ↓
Materiality assessment
    ↓
Development and testing
    ↓
Validation and approval gates reopened as required
    ↓
Controlled release
```

Change materiality follows effect on behaviour, assumptions, data, use, regulatory status and dependencies, not the size of the code change.

### Where it sits

```text
Upstream:   Monitoring breach · Validation finding · Business change
This:       Change classification and governance
Downstream: Testing · Revalidation · Approval · Deployment
```

### Ownership

| Role | Responsibility |
| :--- | :--- |
| Model owner / developer | Proposes change and materiality |
| MRM / validation | Challenges classification and validates as required |
| Approval authority | Approves material changes or exceptions |
| Technology | Releases authorised versions only |

### Permanent rule

A one-line parameter or transformation change can materially alter outputs. Technical size is not model-risk size.

### Never confuse [Recalibration] and [Redevelopment]

**Recalibration** - updates parameters or level alignment while preserving the essential structure and intended use.

---

**Redevelopment** - materially changes structure, drivers, architecture or assumptions and therefore creates substantially new development evidence.

### Permanent trap

Keeping an overlay indefinitely because it is easier than fixing the model. Temporary mitigation needs an owner, rationale, review point and exit criterion.

### Jurisdiction variants

| Jurisdiction | Change rule | Delta / status |
| :--- | :--- | :--- |
| US | Deviation can trigger adjustment/recalibration/redevelopment; validation follows change scope/frequency. | No fixed schedule. |
| UK | Proportionate governance/validation/mitigants. | SS1/23 applies. |
| EU | Internal control + CRR/ECB change process. | Approval/notification may apply. |
| IN | Draft: post-change/trigger validation + formal approval. | Draft as at August 2026. |

<Recall
  q="When is recalibration the wrong response to deterioration?"
  a="When the model structure, variables or assumptions are no longer sound; changing parameter levels cannot repair structural misspecification."
