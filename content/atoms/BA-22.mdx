Scope changes are inevitable, but on a regulatory program the deadline is set by law. Every requested change must go through a structured change request process. The BA must document the change, analyze its impact on schedule and cost, and present to the Change Control Board. If adding new requirements, either find efficiency elsewhere or request additional resources (often hard to get). The key is *trade-offs*: for example, if a late rule change is issued, you might push some non-essential enhancements to the next phase. All approved changes and their rationales should be logged in a change control log.

No unapproved scope creep should occur: formal approval (by business, risk, audit) is required for anything beyond original scope. In practice, regulators expect that the project was baselined and any changes are traceable. A formal change control ensures auditors see an audit trail of decisions (who approved a change and why).

<Rule label="PERMANENT RULE">
Always process scope changes formally. Do not slip regulatory deadlines. If new items arise late, escalate them to executives and re-prioritize or delay less-critical work.
</Rule>

<Trap label="PERMANENT TRAP">
Allowing uncontrolled additions to scope (scope creep) because of “just this one change.” Each change must consider the fixed deadline. Avoid informal side agreements to implement extra features without updating the project plan.
</Trap>

<NeverConfuse>
**Scope Change** vs **Scope Creep**:  
*Scope Change* is a formally approved modification with documented impact analysis. *Scope Creep* is uncontrolled expansion of scope. A regulated project should only have intentional scope changes through proper channels.
</NeverConfuse>
